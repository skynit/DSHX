# 手机内创建和运行应用

DSHX 提供通用微应用能力：用户在设置描述需求，dsh 编写页面和 JavaScript 逻辑、生成应用包，宿主检查安装后在 DSHX 内打开运行。也可在应用详情或打开后的标题栏使用“打包 APK”，导出带独立桌面入口的安卓应用。便签、计算器、文本整理等可以只使用页面和数据；广告跳过属于可选手机自动化用途。

## 组件和职责

| 名称 | 是什么、由谁创建、负责什么 |
|---|---|
| 宿主 | 用户安装的 DSHX，提供应用管理、网页容器、系统授权和真实手机动作 |
| dsh | DSHX 内运行的智能体引擎，理解需求、编写和检查应用；应用日常执行不需要持续调用模型 |
| 制作技能 | APK 内置的 `create-dshx-app` 文件夹，启动时准备到 dsh 技能目录，教智能体使用真实应用接口；技能本身不运行应用 |
| 应用包 `AppPackage` | 由 dsh 生成的 `app.json`，包含清单、HTML页面、JavaScript脚本、样式、设置和能力声明；解析器检查结构而不证明脚本行为 |
| 应用管理 `AppStore` | `DshApp` 创建，独立于 Node 保存版本、内容摘要、启停、配置、操作回执及每应用数据 |
| 应用宿主 `AppHost` | DSHX 进程创建，给应用页面及可选后台入口各建独立 Android WebView；WebView 是 Android 系统提供的网页执行组件 |
| 应用接口 SDK | 宿主先于应用代码注入的 `dshx` JavaScript对象，使用异步消息调用存储和手机能力，不暴露模型凭据或任意 Android 对象 |
| 后台入口 | 应用清单可选的 JavaScript文件，启用后由宿主运行；与打开的页面不共享JavaScript变量，共享本应用独立存储 |

## 使用流程

1. 打开“设置 → 微应用 → 添加”，填写需求，点击“让 dsh 创建”。需要 dsh 运行且模型能正常工作；随后进入普通会话，可以继续补充需求。
2. dsh 读取内置技能、查询 `app_status`，编写 `web-v1` 应用包，检查后调用安装接口。安装、更新和回滚均默认停用。
3. 返回设置查看应用说明及能力，启用后点击“打开应用”。普通页面应用无需选择手机应用，也无需开启无障碍服务。
4. 需要操作其他应用时，再选择适用范围、开启手机总开关并在系统授权无障碍服务。
5. 关闭页面只关闭页面上下文；可选后台入口继续运行。停用、删除、更新或配置变化会关闭相应上下文并撤销尚未派发动作。

不配模型也可从添加窗口安装两个完整示例：“随手便签”验证输入和持久保存；“广告跳过示例”验证后台事件和手机接口。示例是普通应用包，宿主没有为它们写专用业务规则引擎。

## 运行边界

应用页面和后台脚本来自已检查包的内存内容，通过每应用独立的虚拟 HTTPS 来源提供。禁止文件及内容URI访问、其他应用来源、远程页面导航、网页框架、网页插件及工作线程。网络请求只允许清单声明的 HTTPS来源，且仍受服务端跨来源访问规则约束。

SDK 通过只发给该应用顶层页面的消息端口连接；消息端口是宿主与网页交换请求和结果的专用通道，没有向网页暴露任意原生对象。宿主在每次调用时核对应用当前版本、启停状态、声明能力和输入限额。页面与后台入口有不同观察归属，不能互相或覆盖聊天中的有效手机观察。

应用可执行标准网页逻辑，不限制为规则语言。独立 JSON数据通过宿主接口保存，不依赖 localStorage。原生插件、摄像头、任意Android API、定时唤醒等未开放能力需另外扩展宿主，不能由技能文件凭空提供。

后台不是永久保活服务。Android 终止 DSHX进程时应用停止，重新启动DSHX后恢复已启用后台入口。停止 dsh只停止智能体引擎，不主动停用微应用；要停止应用使用各自开关。脚本错误、网页运行进程退出及外部包变更需明确显示或记录，不能视为业务成功。

## 手机扩展示例

无障碍服务把选定范围内的界面变化合并后通知应用。后台脚本可请求真实完整组件树，自行决定是否匹配，再请求唯一目标的点击。这里的“完整组件树”包含容器、父子关系、真实控件标识和动作信息，而普通手机观察默认优先返回可见内容。

手机调用沿用总开关、锁屏息屏、有效观察凭据、位置与遮挡检查，且派发前重新校验所观察的树。聊天手机任务优先。读取截断、不可读分支、页面变化或观察属于其他任务时拒绝动作。点击回执不代表业务目标完成，需要应用重新观察确认；失败、超时或未知结果不自动重放。

GKD是用户给出的功能示例参考，不是本平台应用格式。当前没有导入GKD订阅或复制其选择器代码；不宣称兼容GKD的规则生态。

## 保存和管理接口

`app_status`、`app_check`、`app_install`、`app_enable`、`app_disable`、`app_logs`、`app_rollback`、`app_remove` 八个工具经现有认证连接调用原生管理对象，须有有效 Full会话。管理接口不会伪造手机会话。列表状态只返回清单摘要；按应用编号查询才返回完整包，避免列表挤入所有源文件。

全局状态修订号用于检测管理操作的并发冲突，每应用另有自己的运行修订号；修改其他应用不销毁当前页面。设置页自动刷新保留未保存草稿，发现同一应用已被修改时提示冲突并要求显式重新读取，避免覆盖输入。启用偏好、后台实际启动与运行故障分开显示。

修改携带稳定 `operationId` 和最新 `expectedRevision`。同编号同内容返回原回执，旧状态不能覆盖新设置。内容摘要、检查标识过期、同版本冲突、历史版本校验及原子写入防止半安装或错误覆盖；损坏文件保留，外部包变更暂停执行。

包保存在 `files/micro-apps/packages/<id>/<version>/app.json`；状态及历史摘要在 `files/micro-apps/state.json`；独立数据在 `files/micro-apps/data/<id>/storage.json`，最近运行记录在同目录 `events.jsonl`。包及每应用数据各≤1MiB，每包≤64个文本文件，运行记录最多500条，修改回执最多100条。日志不保存屏幕正文或截图。

现有 Full文件和命令仍能访问已有权限范围，应用容器的资源限制不等于整个dsh文件系统已有强隔离。当前微应用不包含在现有会话备份或知识归档中。

字段、SDK、示例和完整制作流程见 [制作技能](../app/src/main/assets/skills/create-dshx-app/SKILL.md)及[运行契约](../app/src/main/assets/skills/create-dshx-app/references/runtime.md)。


## 导出独立 APK

**APK** 是 Android 安装包，由原生“打包 APK”操作在手机内生成并签名。**运行壳**是 `micro` 模块构建的精简安卓程序，包含系统 WebView 页面承载、设置、独立存储与按需手机能力；它复用 `AppPackage`、`AppStore`、`AppHost`、`AppPhone`、`PhoneService` 的源码，不包含 Node、聊天引擎、模型配置或语音库。**签名**是 Android 判断应用发布者与更新兼容性的凭据，由本机 AndroidKeyStore（系统私钥保存服务）创建并保存，不写入 APK。

用户流程：创建并安装微应用 → 打开详情或应用页面 → 点击“打包 APK” → 等待本机组装和签名校验 → 在系统文件界面选择保存位置 → 将 APK 传到安卓手机安装。打包不依赖 dsh 是否启动，也不要求先启用该微应用。

导出过程重新校验已安装定义，只写入规范化 `app.json` 和精简运行壳。包名由微应用编号的 SHA-256 摘要稳定生成，不同微应用可以同时安装。应用名、版本名来自已检查清单；Android 用于比较安装先后的整数版本号由本机逐次登记，重复打包同版本复用编号，切换定义版本时递增。每个包生成后使用 APK v2 签名，再校验签名，成功后才进入系统保存文件流程；失败删除临时产物。

导出不带 DSHX 内已有数据、运行记录、用户设置或其他应用的授权范围。安装后纯页面应用使用默认设置，可直接打开。需要屏幕能力的应用默认停用，用户在独立应用的“设置”中重新选择适用应用、开启该 APK 自己的无障碍服务并启用；独立应用的启用开关同时承担手机操作总开关。手机范围、亮屏解锁、观察有效期、节点完整性、派发前复查等仍由共用原生代码检查。独立应用没有聊天任务，因此不需要 DSHX 的聊天任务调度。

声明 `background` 的应用启用后使用常驻通知运行后台脚本，通知与应用设置均可停止。系统终止进程或用户强行停止后，不能承诺永久运行或系统定时唤醒。未声明后台入口的应用没有后台服务；未声明 HTTPS 来源的应用没有联网权限；未声明屏幕能力的应用没有无障碍服务。

在同一份 DSHX 安装中再次打包同一微应用，会复用系统保存的签名密钥和包名，目标手机可以覆盖安装，自己的存储数据保留。微应用版本更新后重新检查安装，纯页面恢复启用，屏幕功能暂停并保留目标手机原设置供重新启用。清除 DSHX 数据、卸载 DSHX 或换用另一台打包设备后，不能保证拿到原私钥，因此新包不能作为原签名应用的覆盖更新；已经安装的独立应用仍可使用。当前导出沿用项目 Android 8.0 / API 26 最低支持与 targetSdk 28 的手动安装路线，未承诺应用商店发布。

实现入口：`AppApk` 读取已校验包，使用 ARSCLib 修改运行壳中的应用清单和资源包名，再由 Android 官方 apksig 库签名与验签；`AppsSettings` 负责进度、错误和系统文件保存。开发机正常构建 `:app` 时会先构建 `:micro:assembleRelease`，将未签名运行壳作为生成资源放入 DSHX，无需手工维护二进制模板。
