# 在对话中创建应用

在用户当前的 dsh 对话中，把需求做成能打开、操作、保存数据的应用，并按需交付 APK。使用中文说明和界面文案。用户无需先进入创建页面；页面入口也沿用本技能。不要把所有应用都设计成自动点击规则。

## 接收对话需求

普通聊天可自动选用本技能，用户也可显式输入 `/create-dshx-app 帮我做一个记账本，直接给 APK`。已收到本技能正文时直接执行，不重复加载。

| 用户说法 | 本轮目标 |
|---|---|
| “帮我做个待办应用，能保存记录” | 制作并安装微应用 |
| “做一个记账本，给我 APK” | 制作应用，继续打包并交付 APK |
| “把刚才的应用打包成 APK” | 读取已有应用的当前版本并导出，复用已有实现 |
| “给刚才的应用加分类” | 读取当前包，保留数据格式，增加版本并更新 |

沿用当前会话中的需求和应用编号，继续在当前对话报告进展、修改和交付。用户只要求制作应用时默认交付微应用；明确要求 APK 或安卓安装包时交付 APK。后续要求优先于早先选择。需要打包但无法从对话或应用列表确定目标时，只询问要打包哪个应用。

## 分清产物和运行者

- **宿主**是手机已安装的 DSHX。它提供应用列表、网页运行容器、存储和受限手机接口。
- **dsh**是宿主内的智能体引擎，负责理解需求、编写文件、检查并安装应用。运行已安装应用无需持续调用模型。
- **技能**是本文件及参考资料，只教你创建应用，不是应用运行程序。
- **应用包**是你生成的 `app.json`，包含清单、页面、脚本、样式、设置及能力声明。宿主实际接受后才算安装。
- **后台入口**是包内可选的 JavaScript 文件，由宿主在应用启用后运行。它与用户打开的页面各有独立网页上下文，通过本应用存储交换数据。

## 先查能力，再选择实现

调用实际提供的 `app_status`，阅读 [运行契约](references/runtime.md)。以返回的格式、接口、限额为准，不臆造工具和手机权限。

普通记录、计算、整理、交互工具优先使用 HTML、CSS 和 JavaScript；需要保存时声明 `storage`；需要访问服务时填写准确的 HTTPS 来源；只有有持续事件逻辑时才增加后台入口。手机能力是可选扩展，不是应用的定义。

修改现有应用时，先 `app_status({id})` 读取完整当前版本，保留用户数据格式并增加版本号。用户只询问方案时解释，不默认安装；用户明确要求制作时完成实现和检查，不停在建议层面。

先用一句话说明要做的应用和交付形式，再开始制作。待办、记账、便签、计算和文本整理等明确需求直接做出可用初版；仅在缺少会影响核心行为的信息时提问。制作、安装、打包与验证进度以实际结果为准，不能把会话已创建称为应用已完成。

能力不够时说明具体缺口，例如摄像头、任意 Android API 或系统定时唤醒尚未开放。可以交付有用的受支持部分，但须说清区别，不能伪造功能或用 shell、后台 dsh 循环代替宿主能力。

## 编写应用

在当前真实工作目录创建草稿目录，保存 `app.json` 及简短使用说明。可以先编写独立源文件，再使用脚本把 UTF-8 内容放入 `files`，不要手工反复转义长脚本。

清单格式为 `web-v1`；HTML 入口必须真实存在于 `files`；脚本、样式、数据文件也都必须打包。SDK（宿主注入的 JavaScript 接口）名为 `dshx`，在应用脚本前注入；调用前等待 `dshx.ready`。不要自己替换 SDK、读取其他应用文件或宿主模型凭据。

从最接近的可运行示例起步：

- 页面和数据工具：[便签应用](assets/quick-notes.json)。它演示输入、异步保存、失败提示和重新打开后恢复。
- 手机自动化：[广告示例](assets/skip-startup-ads.json)及[广告场景说明](references/ad-skip.md)。它演示按事件执行普通 JavaScript，而不是宿主写死的广告规则。

页面须有明确主要操作、加载与错误状态；按钮至少 48 CSS 像素高。复用暖中性色、低对比边框、克制强调色，适配明暗主题和系统字体放大。不要使用大脑图标，不给产品页面塞安装协议和实现细节。

只有脚本会读取的设置才应出现在清单里，通过 `dshx.info().settings` 使用；不要添加没有执行语义的开关。修改宿主设置会重新创建后台入口，页面可能需要重新打开。

## 检查实际行为

1. 检查包内路径、入口及引用；用当前可用的 JavaScript 运行环境做语法检查，不能把 JSON 解析成功当作脚本可运行。
2. 对核心逻辑做必要验证：计算结果、空数据、保存与恢复、网络失败。后台功能还要检查并发事件、停用、超时和未知动作结果。
3. `app_check({package})` 让宿主检查包结构、能力、路径和大小。这不是界面检查或脚本执行证明。
4. 用户允许手机操作时，用实际工具打开并验证页面；需要组件树时使用 `phone_observe({tree:true})`，保留真实控件标识及父子关系。不猜包名、控件编号或页面内容。

不要为了测试擅自访问付费服务、发送消息、修改真实业务数据或开启持续手机操作。按用户已授权的范围推进，不对同一步骤反复确认。

## 安装和交付

制作或更新应用按下面顺序完成；仅导出已有应用时从第 4 步开始：

1. `app_check({package})`：传入解析后的完整 `app.json` 对象，不传草稿路径。包有修改后重新检查。
2. `app_status({})`：读取最新顶层 `revision`；为本次安装生成稳定 `operationId`。
3. `app_install({checkId,hash,operationId,expectedRevision})`：使用检查结果和状态中的原值，安装为停用。
4. `app_status({id})`：核实目标应用的实际版本与状态。微应用交付到此完成；APK 交付继续下面的导出步骤。

用户要求 APK 时，继续调用 `app_export({id,version})`，版本来自第 4 步的当前状态。宿主在手机内组装、签名并验签，返回 `path`、`name`、`size`、`sha256` 和 `signatureVerified`。随即用 `present({files:[{path,description}]})` 在当前对话交付返回的真实路径；不要止于告知用户去页面手动打包。备用保存入口是“设置 → 微应用”中 APK 文件右侧的保存按钮，无需再次打包。打包失败时保留已安装的微应用，说明失败步骤；版本变化时重新查询后再导出。

微应用完成后告知“设置 → 微应用”的应用入口，由用户查看能力、启用并打开；创建过程本身不依赖用户去该页面。APK 模式下安装微应用只是制作中间步骤，无需先启用它即可导出，目标手机也不需要 DSHX。已有微应用仍可在详情或打开后的标题栏使用“打包 APK”。独立 APK 不带已有使用数据或授权范围，屏幕功能需要在目标手机重新设置并授权。普通应用无需选择手机应用或开启无障碍；用户已经明确授权启用时可调用 `app_enable`。

安装超时先用 `app_status({operationId})` 查回执，并用 `app_status({id})` 核实当前版本；重发原请求时保留原编号及全部参数。明确收到修订冲突且核实本次安装未完成时，刷新修订后可重试一次；检查失效时重新检查。成功记录的操作编号不能用于改变参数的请求；结果仍未知或再次失败时保留草稿并报告阻碍。不要直接写宿主 `micro-apps` 安装目录，也不要伪造手机会话。管理工具不可用时说明需要当前 dsh 的 Full 会话；不得用开发机 Gradle、ADB 或普通插件安装冒充手机内的制作交付。

交付回复保持简短：说明已完成的功能、应用入口或 APK 附件、已验证与未验证部分。有后台功能时补充停用方式。源码或 JSON 草稿不能替代用户要求的 APK；签名通过不表示已在目标手机安装或完成业务验证。工具缺失时可保留草稿并明确当前未安装或打包。
